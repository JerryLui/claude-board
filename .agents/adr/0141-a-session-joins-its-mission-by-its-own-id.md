# 141. A session joins its mission by its own id, one at a time, and takes the PM's orders

2026-10-30, amends 123, 129, 131; relates to 125, 126

**Context:** a mission's session was named by `CLAUDE_MISSION` in its environment, which the launcher set and every shim read, so a board linked by whatever environment a process inherited: a later background session on the same login was read as the mission's, and a tab the person started by hand could never become one. Keeping the variable and adding a by-hand route beside it was on the table, and would have kept two ways to name a mission and the leak with them. **Decision:** no environment names a mission. A session joins one (`POST /api/mission/:key/join`) by its own session id, which the agent reads fresh at each call since a `/clear` changes it, beside its process (`pid`, `procStart`), which a `/clear` keeps; the same process under a new id is the same session and takes the id, and the shim never supplies an id of its own. A join onto another live session is a 409; with `takeover` it is pending, the bound session reads it on its binding (`GET /api/binding`, off the stored records alone, cheap enough for a hook every minute), finishes its step, writes its handoff and leaves, and the leave binds the one that asked, so a mission never has two sessions. A leave with nothing pending stores `session: { ended, leftAt }`, and that session is a tab card again. A board post naming no mission links to the mission its posting session is bound to; an explicit `mission` still links, for any agent. Orders gain `pm`, the PM's words the Master Chief carries word for word, secret only, which the bound session marks `seen` (`ackedAt`, shown on the card) and the Master Chief marks `resent` once. **Consequences:** a board posted by a mission's session before its join belongs to no mission; a session bound by id alone is told from another only by its id, as before (129), and a pid names a session only beside its process start, so a record bound by pid alone is matched by its id; a session holds one mission at a time, so it leaves one before it joins the next, and the session a launch replaced cannot join its successor's place, unless it is that session resumed in a new process (the same id, its pid reused under another start or another pid once the old process is gone), which binds and drops `ended` so its beats land; a board keeps the mission it first linked, so a later round on it from a session that has moved on (bound elsewhere, or the one its mission records as ended) is a 400 that asks for `fresh`, and a join or leave through the shim's tool starts the next board itself; a write naming its session beats only as the bound session and never binds one; the board holds who may order only by the secret, and the session trusts an order by its sender (126's footing), not by anything on the board.
