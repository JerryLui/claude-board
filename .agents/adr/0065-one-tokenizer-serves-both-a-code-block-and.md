# 65. One tokenizer serves both a code block and a markdown fence

2026-08-09

**Context:** ticket 04 needed a fenced code block inside markdown to highlight through the exact same path as a `kind: 'code'` block (AC 14) — `TOKEN_CLASS`/`highlightRows`/`flattenTokens`, all in `src/render.mjs`. But `src/markdown.mjs` already sits upstream of `src/render.mjs` through `src/board.mjs`, which imports `mdToHtmlAndAnchors` from the former and `renderBlock` from the latter (entry 38's existing circular edge, safe there because neither side calls the other at module-evaluation time) — so a direct `markdown.mjs -> render.mjs` import would close a second cycle through the same bridge. **Decision:** `render.mjs` exports `highlightFenceHtml`; `board.mjs`, the one module already positioned above both, passes it into `mdToHtmlAndAnchors` as an injected `opts.highlight` argument rather than either renderer importing the other. A fence renders through it with no line-number gutter, since it carries no `source.lines` and therefore none of the "file's real line number" entry 63 promises a `kind: 'code'` block. **Consequences:** the tokenizer stays the tree's one tokenize-and-wrap implementation with `board.mjs` its only caller-side wiring; every other caller of `mdToHtmlAndAnchors`/`mdToHtml` (every markdown-only check) keeps today's plain-escaped fallback by simply omitting the argument.
