# 130. A mission's last state is released, and landed records migrate

2026-10-28, amends 123 and 128; relates to 124, 129

**Context:** a mission's last state was `landed`, which every other surface the person reads uses for a merge, while a merged change may still wait on its deploy, an infra apply or a production check; the board named the work finished before it was in production. Keeping `landed` and adding a separate released state was on the table, and would have left two finished-looking columns and a stop hook choosing between them. **Decision:** the last stored state is `released`, written once every release step after the merge is walked, with `releasedAt` in place of `landedAt`; between merge and released a mission is working, or needs you while a step waits on the person. A record stored `landed` is rewritten as `released` at the daemon's start, before it serves, and reads as `released` meanwhile; a write carrying `state: 'landed'` is stored as `released`, so a session open across the rename keeps working. `GET /api/missions` counts `released` in place of `landed`, the home page's last column is Released, and the Missions notification says released. **Consequences:** `landed` stays accepted on write for good, since nothing tells when the last session that writes it has closed; a reader of the raw files after a start finds no `landed`, and one of an old backup still reads it as `released`.
