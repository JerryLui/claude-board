# 149. Ten background sessions work at once, fourteen alive; the PM's tab holds no slot

2026-11-09, amends 129, 148

**Context:** at eight working and twelve alive (148) launches queued while the PM's own tabs, each bound to a mission by `/mission NAME`, held slots the Master Chief's background sessions needed. Those tabs are the PM's attention, not the load the caps meter, and the session watcher already tells them apart: each snapshot entry is `interactive` or `bg`. **Decision:** `MAX_WORKING` is 10 and `MAX_ALIVE` 14, the PM's pick. The launch caps' counts (`live`, and the launch check) skip a mission whose bound session the latest snapshot lists `interactive`; `listed()` carries each entry's `kind` for it. A launch's bare reservation, a session the snapshot does not list, and one matched by id alone in another process (the watcher lists one process per id, so a tab there can hide a working background session) still count, and while the watcher reads down every live session counts. `GET /api/missions` answers `slotFree`, a launch now would not queue, so `~/.claude/scripts/board-wait.mjs` reads it and no longer copies the numbers. Rejected: counting tabs at a higher cap, which still lets the PM's tabs queue background work; deriving the exemption from `jobId`, which the same registry file carries, so it is no harder to forge; `kind` is a cooperative signal, as the caps are a scheduling rule, not an enforcement boundary. **Consequences:** a tab joined to a mission no longer holds a slot, so up to ten background sessions work beside any number of tabs, against the heavy gate's memory budget; the numbers live here and in the Master Chief's Caps rule as information only; a board-wait reading a daemon without `slotFree` never wakes for a slot, so the board installs first.
