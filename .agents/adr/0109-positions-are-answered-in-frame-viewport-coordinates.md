# 109. The positions payload is answered in frame viewport coordinates

2026-08-20 · relates to 99

**Context:** the stage's `positions` answer to `locate` carried `{left, top}` relative to the stage document's `<body>` (the element's client rect minus the body's own box), while the pin layer it feeds overlays the iframe viewport. The two agree only at scroll 0 on a marginless body, and they agree for exactly one scroller: the body box moves with whichever element actually scrolled, while the layer stays where it was, so a pin on an artifact whose scroller is an inner pane drew offset by the body's displacement. PROTOCOL.md's own "Changing this file" rule bans repurposing an existing field without the ADR treatment, and ADR 99 is the shape that exception takes. **Decision:** the `positions` payload's `{left, top}` now means the element's own client rect — frame viewport coordinates, nothing subtracted — instead of a position relative to this document's `<body>`. Every consumer moved in the same commit: the stage-side `locate` branch in `stageAgentScript` (src/render.mjs) stops subtracting the body box; the parent-side `handleStagePositions` and `requestStagePositions` (src/ui.mjs) draw exactly what they are answered, with no offset bookkeeping of their own; and the two test files that pinned the old meaning (test/check-click-pin.mjs, test/check-page-board.mjs) flip to recomputing the element's own client rect independently. An element scrolled out of the frame reports a position outside the frame's box, which the pin layer's own overflow clip hides. **Consequences:** no cross-version skew is possible — both halves of the channel ship inside one rendered page (content-addressed siblings plus inlined srcdoc), so there is no deployed consumer still holding the old meaning. PROTOCOL.md's `positions` row is reworded in the same commit, and a pin draws on its element for every scroller at once, with no per-scroller offset to remember.
