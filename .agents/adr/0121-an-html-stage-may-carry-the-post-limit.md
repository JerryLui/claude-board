# 121. An html stage may carry the post limit

2026-10-19, amends 7; relates to 112, 117; amended by 122; narrowed by 136

**Context:** a stage carrying evidence inlines its clips and full-size screenshots as `data:` sources (a self-contained stage loads nothing else), so one evidence page passes the 512 KiB block cap with its shots alone, while a post may already carry 25,000,000 bytes spread across many blocks. The block cap had been the bound on every single-threaded pass over one block, and measured at 24 MB it was hiding four costs: a `<!` declaration or close tag with no `>` rescanned the rest of the stage from every start (188 s for 1 MB of `<!`), an unmatched close walked the open-element stack (14 s for 1 MB), the anchor tree took about 400 bytes of heap an element (1.8 GB for 24 MB of `<div>`, against a 4.4 GB heap), and the hint check read an element's whole text once per comment (240 ms a comment on a 24 MB `<pre>`). **Decision:** an `html` block, by value or by file reference, wherever it sits, is capped at 25,000,000 bytes, the post limit, in place of 512 KiB, and the `html` blocks in one post share those 25,000,000 bytes, so a post naming several large stage files is refused as a post carrying them by value is; every other block and every by-value string keeps 512 KiB; the four costs are fixed in the anchor parser rather than kept behind the cap, the tree stopping at 524,288 nodes (as many as a stage under the old cap could produce). **Consequences:** a stage of a few large `data:` sources costs about 50 ms a render and 300 ms a submit at 24 MB; a stage dense with markup costs about 1 s a render and 2 s a submit at 24 MB, as 25 MB spread over 47 stages already did; an anchor on an element past the 524,288th node of a stage resolves lost; the page carried the stage twice (in the frame's `srcdoc` and in the board data the client hydrates), so a 24 MB stage served a 48 MB page and every push after a submit carried it again, until ADR 122 had a page carry each stage once.
