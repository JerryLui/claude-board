# 78. The `select` message is deleted; a stage may propose, never decide

2026-08-01

**Context:** an earlier version had a stage post a content-free `select` on every click, so clicking the visible mock of an `html`-kind option picked that option. Every message on the stage channel is stage-authored input, no different in kind from the mock's own markup: `click` and `hover` only propose an anchor a human still has to submit and `positions` is pure geometry, but a message that picks an option is the agent handing itself the answer to its own question. Two paths made that reachable — the stage's own script can dispatch a click on itself, which an autoplaying mock does for ordinary reasons, and since `cb: 'cb-stage'` is a fixed public string, any stage's script can call `postMessage({cb: 'cb-stage', type: 'select'})` directly. **Decision:** the message is deleted rather than guarded, before the work that added it merged. An `ev.isTrusted` guard closes the first path only and the second forges upstream of any such guard, because validating a message's origin and re-deriving its frame from the live DOM proves that *a stage* sent it, never that *a human* acted. **Consequences:** `.choice-variant .html-stage { pointer-events: none }` is load-bearing rather than cosmetic — a real click over the visible mock never reaches the iframe and lands on the card in the parent document, which is the only thing that records a pick — so an option's stage is a thumbnail to choose between and not a surface to operate, which is what the lens (entry 22) exists to work around; and a forged `select`-shaped message from a live, correctly-addressed stage is inert, because no handler is left to act on it.
