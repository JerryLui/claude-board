# 143. A reinstall fails on a refused read under ~/Documents, after registering

2026-10-30, relates to 15, 100

**Context:** a release passed `install.sh`'s health gate while every board reference under `~/Documents` failed `cannot read <path>: EPERM`: the rebuilt launcher bundle was new code to macOS and had lost its Documents grant, and kickstarts alone did not bring it back. Health proves the daemon answers, not that it can read what a round references. **Decision:** after the health gate, a launcher install asks the daemon, with the secret, to open a file under `~/Documents` the way a reference is opened (`GET /api/probe/documents`, a code back and never a name). Refused, or unanswered within 120 s (a pending prompt holds the open), the health step fails with the steps that granted it again (`tccutil reset SystemPolicyDocumentsFolder io.github.jerrylui.claude-board`, `launchctl kickstart -k gui/$(id -u)/claude-board`, then Allow on the next prompt); the clients are still registered and the manual copied, then the banner names the refusal and the install exits 1. Rejected: a warning with exit 0, the shape of the run that passed; exiting at the health step as its other failures do, which leaves a first install unregistered while the board works for everything else. **Consequences:** a reader who refused the folder on purpose gets exit 1 on every reinstall; the degraded install, which runs as node with no bundle to grant, skips the read and keeps its launcher warning; the clean transcript keeps entry 100's line count, the result riding on the health line. The steps to grant it again are printed for a refused read alone: a read that timed out says so and points at a waiting prompt, one that never reached the daemon says so, and both still exit 1. A listed folder whose first file alone is closed to this user (mode 000, another owner) reads ok, since no grant would change it.
